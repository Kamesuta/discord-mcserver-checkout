# 流用機能 設計方針

## 目的

既存の `ACTIVE` な企画鯖を、利用者が管理者承認なしで次の企画へ転用できるようにする。

- 旧企画の状態はバックアップとして退避する
- サーバーは初期化してから次の企画に引き継ぐ
- サーバー割り当ては維持し、別サーバーの再抽選は行わない
- 履歴は「同じ Workflow を上書き」ではなく「旧 Workflow を返却し、新 Workflow を新規作成」で残す

---

## 現状調査

### 既存の近い機能

- 新規申請: `WorkflowCreateModal` + `workflowService.create()`
- 承認/有効化: `activateWorkflow()` (`src/domain/flows/ActivationFlow.ts`)
- 返却: `completeReturn()` (`src/domain/flows/ReturnFlow.ts`)
- 通知ボード: `NotificationBoardService` (`src/domain/services/NotificationBoardService.ts`)

### 既存実装から見える制約

1. `WorkflowStatus` は `PENDING / REJECTED / ACTIVE / RETURNED` の4状態のみ
2. `NotificationBoardService` の各セクションは `SectionBuilder#setButtonAccessory()` を使っており、各セクションに置ける目立つボタンは1つ
3. 返却は `ACTIVE -> RETURNED` に遷移し、サーバーはアーカイブ後に `pterodactylCleanService.reset()` で初期化される
4. 承認は「空きサーバーを探して ACTIVE にする」処理なので、同一サーバー継続利用の流用とは責務が少し違う

---

## 基本方針

### 1. 流用は「旧申請の返却 + 新申請の即時有効化」として扱う

流用専用の中間ステータスは追加せず、下記2件の Workflow を残す。

- 旧 Workflow: `ACTIVE -> RETURNED`
- 新 Workflow: `PENDING` を経由せず、その場で `ACTIVE`

この形にすると、既存の一覧・履歴・アーカイブ命名規則を大きく崩さずに済む。

### 2. サーバーは同じものを使い続ける

`findAvailableServer()` は使わず、旧 Workflow の `pteroServerId` をそのまま新 Workflow に引き継ぐ。

### 3. 流用前に必ずバックアップし、必ず初期化する

要件上「バックアップは取られ、サーバーはリセットされます」が必須なので、流用では `skipArchive` / `skipReset` は持たせない。

### 4. 一般利用者の流用権限は「主催者のみ」を基本にする

既存の返却ボタンはパネルユーザーも押せるが、流用は「次の企画を新規に立てる」操作なので責任範囲が重い。
少なくとも初期実装では、一般利用者の流用は旧 Workflow の `organizerDiscordId` に限定する。

管理者が代行する必要がある場合は、別途 `mcserver-op` 側に追加する余地はあるが、初回スコープには含めない。

### 5. 新企画の主催者は変更しない

ボード起点の UX と既存モーダル再利用を優先し、新 Workflow の `organizerDiscordId` は旧 Workflow の主催者を引き継ぐ。

- 変更するのは企画名 / MCバージョン / パネルユーザー / 補足説明
- 主催交代を伴うケースは流用対象外とし、通常の新規申請で扱う

## ユーザー導線

### `/mcserver reuse`

一般利用者向けコマンドとして追加する。

- 引数: `id`
- 対象: 自分が主催者の `ACTIVE` Workflow
- 実行すると流用モーダルを開く

モーダル入力項目は既存の `WorkflowBaseCheckoutModal` をベースにする。

- サーバーの用途/企画名
- Minecraft バージョン
- パネル権限を付与する人
- 補足説明

`organizer` はコマンド引数にせず、旧 Workflow の主催者を引き継ぐ。

主催者変更は許可しない。
これは既存企画の継続ではなく新しい申請判断が必要なケースとして扱う。

特に `企画名` と `補足説明` は、流用時にダイアログで毎回入力してもらう前提にする。
既存値を初期表示するかどうかは実装時に決められるが、少なくとも利用者が内容を確認・更新して送信する導線を必須にする。

### ボード下部の流用ボタン

通知ボードの一番下に `流用する` ボタンを追加する。

理由:

- 現在の PENDING / ACTIVE セクションは accessory ボタンが1つずつ埋まっている
- 「ACTIVE セクションの右側ボタンを差し替える」と既存の返却導線を崩す
- 最下部に独立ボタンを置く方が、要件どおりかつ既存 UI への影響が小さい

ボタン押下時の流れ:

1. `ACTIVE` な自分の Workflow 一覧を Select Menu で表示
2. 対象を選択
3. 流用モーダルを表示
4. 確認画面を出して実行

## 処理フロー

### 1. 対象 Workflow の確定

- ステータスが `ACTIVE`
- `pteroServerId` が存在
- 一般利用者は `organizerDiscordId === interaction.user.id`
- `mcserver-op` 権限者を許可するかは実装時に分岐可能にしておく

### 2. 新 Workflow の内容を作成

`workflowService.create()` を使って新 Workflow を `PENDING` で作る。

- `applicantDiscordId`: 実行者
- `organizerDiscordId`: 旧 Workflow の主催者を引き継ぐ
- `panelUsers`: モーダル入力値
- `periodDays`: 既存の新規申請と同じ自動計算ロジックをそのまま使う

つまり、流用後の期間は「残日数の引き継ぎ」ではなく「新規申請時と同等に再計算」でよい。
日付が入っている場合はそのイベント日に応じて、日付がない場合はデフォルト貸出期間で新しく開始する。

### 3. 流用本処理

新規に `ReuseFlow` 相当の処理を用意し、責務を明確に分離する。

推奨ステップ:

1. サーバー停止
2. 旧 Workflow のアーカイブ作成
3. サーバー初期化
4. 旧 Workflow を `RETURNED` に更新
5. 新 Workflow を同一 `pteroServerId` で `ACTIVE` 化
6. サブユーザー同期・Description更新
7. 利用者向け通知
8. 通知ボード更新

### 4. アーカイブ命名

アーカイブは旧企画の履歴なので、命名に使う Workflow は旧 Workflow を使う。
ここは既存 `completeReturn()` と同じ扱いにする。

### 5. 権限同期

新旧でパネルユーザーが変わる可能性があるため、`updateServerSettings()` による再同期を必ず走らせる。

これにより:

- 不要になったユーザー権限を外す
- 新しいユーザー権限を付ける
- Description を新企画名に更新する

## 既存コードの再利用方針

### 再利用するもの

- モーダル項目抽出: `WorkflowBaseCheckoutModal`
- 新規 Workflow 生成: `workflowService.create()`
- サーバー設定同期: `updateServerSettings()`
- ボード更新: `notificationBoardService.updateBoard()`
- アーカイブ: `archiveService.archiveBackup()`
- 初期化: `pterodactylCleanService.reset()`

### 分離した方がよいもの

`completeReturn()` をそのまま呼ぶと、

- 旧 Workflow を `RETURNED` にする責務
- 新 Workflow を `ACTIVE` にする責務

が混ざって扱いづらい。

そのため、返却フローの一部を小さい共通関数に切り出すのは有効。

候補:

- `archiveAndResetServer(...)`
- `buildArchiveNameFromWorkflow(...)`

ただし、初回実装では無理に大きくリファクタリングせず、`ReuseFlow.ts` で必要最小限の共通化に留める。

## データモデル方針

Prisma スキーマ変更は初回不要とする。

理由:

- 履歴は旧 Workflow / 新 Workflow の2レコードで表現できる
- アーカイブ履歴は既存の保存先命名で追跡できる
- 「どの Workflow から流用されたか」は運用上あると便利だが、まずは必須ではない

将来的に監査性を上げるなら、下記のどちらかを追加する。

- `Workflow.reusedFromWorkflowId`
- `WorkflowTransitionLog` テーブル

ただし今回は見送る。

---

## 確認画面の方針

流用は破壊的操作なので、モーダル送信直後に確認 Embed を出す。

表示内容:

- 旧企画名 / 旧 Workflow ID
- 新企画名 / 新 Workflow ID
- 引き継ぐサーバー名
- 新しい補足説明
- 「バックアップ後に初期化される」旨の警告

確認ボタン:

- `流用を実行`

---

## 通知方針

通知チャンネルには最低限以下を送る。

1. 旧企画の流用完了通知
2. 新企画の貸出開始通知

通知文面は完全に別メッセージでもよいが、実装コストを考えると次の整理が妥当。

- 旧 Workflow 側: 返却通知に近い文面
- 新 Workflow 側: 承認通知に近い文面。ただし「承認されました」ではなく「流用により貸出を開始しました」に変更

さらに、通知チャンネルには「流用した」事実が分かる情報を明示する。

最低限含める項目:

- 転用元の企画名 / Workflow ID
- 転用先の企画名 / Workflow ID
- 補足説明
- サーバーID またはサーバーバインディング名
- 実行者

実装上は、旧企画の返却通知と新企画の貸出通知を別で送ってもよいが、
流用専用の通知メッセージを1通追加した方が監査しやすい。

## 未確定事項

### 1. パネルユーザーも流用可能にするか

初回は主催者限定を推奨。
権限委譲を認めるなら、少なくとも確認文面を強くする必要がある。

### 2. 管理者用の流用コマンドを同時に作るか

運用上は便利だが、一般利用者向け要件だけなら後回しでよい。
ただし管理者向けを後で追加する場合でも、主催者変更を伴う流用は許可しない前提とする。

### 3. 旧 Workflow と新 Workflow の関連をDBで持つか

初回不要。ただし後で管理画面や統計を作るなら欲しくなる。

---

## 採用案まとめ

- コマンドは `/mcserver reuse`
- ボード最下部に `流用する` ボタンを追加
- 流用対象は `ACTIVE` かつ主催者本人の Workflow
- 旧 Workflow は `RETURNED`
- 新 Workflow を新規作成して即 `ACTIVE`
- サーバーは同じ `pteroServerId` を維持
- 主催者変更は不可。必要なら通常の新規申請に寄せる
- 期間は新規申請時と同じルールで再計算する
- バックアップと初期化は必須
- Prisma スキーマ変更は初回なし
